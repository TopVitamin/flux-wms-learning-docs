# 19. 业务系统日志

> 本章定位：整理业务操作日志、系统 SQL 日志、登录日志和打印汇总日志之间的追溯关系。它服务于故障排查、审计和打印责任定位，不是 WMS 业务作业流程。
>
> 来源：`../01-按章节拆分的md文件（1119页版本）/19-业务系统日志.md`；原 PDF 第 1017—1037 页。

## 19.1. 学习重点

1. 业务操作信息以 JSON 维度记录系统交互；系统 SQL 日志以数据库 SQL 执行维度记录交互结果。
2. 两类日志可以通过“日志批次号”或“请求 ID”互相追溯：业务操作信息可以定位 SQL 日志，SQL 日志也可以反查业务操作信息。
3. 业务操作结果代码中，原文明确列出 `1000` 代表执行成功、`9999` 代表执行失败。
4. 用户登录、登录失败和打印汇总是独立的查询模块，不应直接当成库存、订单或任务状态。

## 19.1—19.5. 业务操作、SQL 与打印日志追溯

### 用途

把产品经理在现场排查问题时最常用的日志路径画出来：先看业务请求和结果，再用批次号/请求 ID 深入 SQL；打印问题则进入打印汇总信息。

### 原文依据

- 19.1 业务操作信息、19.2 系统 SQL 日志，原 PDF 第 1017—1026 页。
- 19.5 打印汇总信息，原 PDF 第 1030—1031 页。
- 业务操作信息和系统 SQL 日志可通过“日志批次号”或“请求 ID”关联。
- 打印汇总信息可按单证编号或模板名称查询上一次打印和打印明细。

```mermaid
flowchart TD
    OPERATION[用户在 WMS 中执行一次业务操作]
    BUSINESS[“业务系统日志”→“业务操作信息”<br/>输入条件并查询]
    JSON[查看输入 JSON、业务数据、系统输出]
    RESULT{结果代码}
    SUCCESS[1000：执行成功]
    FAILED[9999：执行失败]
    KEY[取得日志批次号或请求 ID]
    SQL[“业务系统日志”→“系统 SQL 日志”<br/>用批次号/请求 ID 查询]
    SQL_DETAIL[查看 SQL 执行结果、返回信息<br/>及异常 SQL 信息]
    TRACE[用于故障检查或性能优化参考]
    PRINT[“业务系统日志”→“打印汇总信息”]
    PRINT_QUERY[按单证编号或模板名称查询]
    PRINT_DETAIL[查看上一次打印信息<br/>及打印明细、打印机/工作站等信息]

    OPERATION --> BUSINESS --> JSON --> RESULT
    RESULT -->|1000| SUCCESS
    RESULT -->|9999| FAILED --> KEY --> SQL --> SQL_DETAIL --> TRACE
    SUCCESS --> KEY
    OPERATION -.-> PRINT --> PRINT_QUERY --> PRINT_DETAIL
```

### 编号说明

1. **1—4：业务操作日志。** 进入业务操作信息，查询并查看输入 JSON、业务数据和系统输出。
2. **5—8：SQL 追踪。** 不论结果成功或失败，都可以使用日志批次号或请求 ID 到系统 SQL 日志中定位详细 SQL；失败结果可以进一步查看异常 SQL 信息。
3. **9—11：打印追踪。** 打印问题进入打印汇总信息，按单证编号或模板名称查询累计信息和打印明细。

### 关键说明

- 日志追踪链是“业务请求 → JSON 记录 → SQL 记录”，不是“业务操作 → 自动修改库存”的业务流程图。
- 打印汇总信息记录打印标记、次数、人员、时间、工作站和打印机等信息，适合排查多打、漏打等问题。

### 事实边界 / 原文未说明

- 原文没有说明日志保留周期、归档策略和日志删除权限。
- 原文没有规定执行失败后的业务补偿动作；日志模块只提供查询和排查依据。
- 用户登录成功、登录失败和打印日志的具体字段很多，本图只保留它们在排查中的入口和用途。

## 19.1—19.10. 业务日志分类与排查入口

> 用途：补齐新版手册的业务操作、SQL、登录、打印、定时任务、DEBUG、数据更新、权限变更和二次审核日志目录。
>
> 原文依据：`../01-按章节拆分的md文件（1119页版本）/19-业务系统日志.md`；原 PDF 第 1017—1037 页。

```mermaid
flowchart TD
    A[业务系统日志] --> B[业务操作信息]
    B --> C[请求 JSON、业务数据与结果]
    C --> D[按日志批次号/请求 ID 追踪]
    D --> E[系统 SQL 日志]
    E --> E1[SQL、分页 SQL 与异常信息]
    A --> F[用户登录信息]
    A --> G[登录失败信息]
    A --> H[打印汇总信息]
    H --> H1[次数、人员、时间、工作站、模板与明细]
    A --> I[定时任务运行日志]
    I --> I1[运行时间、结果与 SQL 日志]
    A --> J[DEBUG 日志]
    J --> J1[临时开启调试模式并查询详细操作]
    A --> K[数据更新日志]
    K --> K1[需开启 DATA_UPDATE_LOG，并按功能配置记录]
    A --> L[用户权限变更]
    L --> L1[记录用户权限增加或减少]
    A --> M[二次审核日志]
    M --> M1[记录二次审核人、时间与操作]
```

### 关键说明

1. 业务操作信息可以沿请求 ID 或日志批次号继续定位 SQL；打印汇总信息用于排查多打、漏打和责任定位。
2. DEBUG 日志会影响性能且只保留短时间记录；原文说明需要谨慎开启并及时查询。
3. 数据更新日志、用户权限变更日志与 GSP 跟踪要求相关；二次审核日志单独记录需要二次确认的操作。

### 事实边界

原文没有说明日志保留周期、统一归档和自动清理机制，也没有把日志记录解释为失败后的业务补偿；本图只表达查询和审计入口。
